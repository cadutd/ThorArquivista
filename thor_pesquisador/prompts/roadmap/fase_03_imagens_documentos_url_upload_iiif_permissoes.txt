Voce e o Codex trabalhando no projeto `thor_pesquisador`.

Objetivo da fase 3:
Adicionar suporte opcional a imagens de documentos vinculadas aos registros dos instrumentos de pesquisa, sem transformar imagem em requisito para o registro dinamico. Um registro pode nao ter imagem, pode ter uma ou varias imagens, ou pode apontar apenas para imagens externas/IIIF.

Estado atual obrigatorio do sistema:
- O repositorio remoto ja contem a fase 2 no commit `18fa98b feat: evolui thor pesquisador fase 2 e crud base`.
- Fase 1 implementada com FastAPI, PostgreSQL, MongoDB, Next.js, dashboard inicial e identidade visual alinhada ao Thor Gestor.
- Fase 2 implementada com Meilisearch, Redis, `index_worker`, busca avancada, facetas, reindexacao e resiliencia para indice Meilisearch inexistente.
- Docker Compose usa `container_name` fixo com prefixo `thor_pesquisador_` e sem sufixo numerico.
- Kubernetes/OKD usa nomes validos com prefixo `thor-pesquisador-`.
- CRUD principal de instrumentos segue a skill `thor-crud-base`: listagem paginada, busca, detalhe, criacao, edicao, exclusao com confirmacao e formulario reutilizavel.
- Registros dinamicos continuam canonicos no MongoDB.
- PostgreSQL guarda usuarios, sessoes, instrumentos, campos, jobs, governanca e agora deve guardar metadados das imagens.
- A pagina inicial autenticada continua sendo `/dashboard`.
- O frontend continua usando `AppShell`, `login_pesquisador.png` e a identidade visual do `thor_gestor_de_arquivos_digitais`.

Skills e padroes Thor a considerar:
- Use obrigatoriamente a skill `thor-crud-base` para qualquer CRUD novo de imagens, vinculos, permissoes ou armazenamento.
- Use a skill `testar-com-docker` para validacao final: backend em container, build frontend Docker e testes funcionais.
- Se for criada navegacao hierarquica de repositorio externo, colecao, dossie, pasta ou estrutura arquivistica, use `thor-lazy-tree`; nao implemente arvore recursiva carregando todos os descendentes.
- Preserve os padroes ja criados no `thor_pesquisador`: camadas de schema, servico, API, testes funcionais, README e manifests OKD.

Contexto:
As imagens sao recursos associados aos registros, nao sao obrigatorias e nao devem dominar o modelo dinamico. O sistema deve aceitar:
- upload para object storage S3/MinIO;
- URL externa;
- manifest IIIF;
- referencia a repositorio externo.

Arquitetura de dados:
- Registros dinamicos continuam no MongoDB.
- Metadados de imagens, armazenamento, direitos de acesso, permissao e auditoria ficam no PostgreSQL.
- O vinculo entre registro e imagem deve armazenar explicitamente `instrumento_id` e `registro_id`.
- A listagem de registros nao deve carregar imagens em massa.
- A visualizacao/detalhe do registro deve carregar imagens sob demanda.
- Para producao em OKD, uploads nao podem depender de filesystem local do pod.
- Para producao, usar armazenamento S3 compativel ou servico institucional de objetos.
- Para desenvolvimento/homologacao, permitir MinIO por Docker Compose/manifests opcionais ou bucket externo.

Escopo funcional:
1. Criar CRUD completo de `imagem_documento` seguindo `thor-crud-base`.
2. Criar tabela `registro_imagem` para vinculo entre registro MongoDB e imagem PostgreSQL.
3. Permitir que uma imagem seja vinculada a mais de um registro quando necessario.
4. Permitir ordenacao de imagens dentro de um registro.
5. Permitir marcar imagem principal/capa por registro.

Regras importantes:

- Excluir um registro nao deve apagar imagem automaticamente se houver outros vinculos.

- Imagens restritas nao devem ser servidas publicamente sem autorizacao.
- IIIF deve ser tratado como referencia externa; nao duplicar binarios quando nao necessario.
